# DroneTM Flight Planner

A standalone, offline-capable flightplan generator for
[plan.drone.hotosm.org](https://plan.drone.hotosm.org). Static page, no backend.

Four steps and a pilot has a mission file for their controller:

1. **Area** - draw it on the map, or upload a GeoJSON.
2. **Flight** - drone, detail (GSD) or altitude, overlap, camera, takeoff point.
3. **Terrain** - one Copernicus GLO-30 crop, stored in the browser.
4. **Generate** - check the summary, download `.kmz` / `.wpml` / `.geojson`.

Only step 3 needs a connection. After it, generating and regenerating works
entirely offline.

## Running it

```bash
cd src/flight-planner
pnpm install
pnpm dev        # http://localhost:3050
pnpm test       # 147 tests
pnpm build      # static output in dist/
```

This is its own pnpm workspace root, deliberately outside
`src/pnpm-workspace.yaml`, so it does not inherit the main frontend's
dependency graph. Same arrangement as `src/drone-mesh`.

## Configuration

| Variable             | Default                    | What it does                          |
| -------------------- | -------------------------- | ------------------------------------- |
| `VITE_MAIN_SITE_URL` | `https://drone.hotosm.org` | Target of the header "Main site" link |

Build-time, like any Vite variable: `VITE_MAIN_SITE_URL=... pnpm build`, or as
a `--build-arg` on the frontend image.

## Deployment

Built into the frontend image (`src/frontend/Dockerfile`, `planner-build`
stage) and served at `/plan`, the same arrangement as `src/drone-mesh`. In
production the Helm chart can also give it its own hostname on the same
CloudFront distribution - see `frontend.cloudfront.subdomainApps` in
`chart/README.md`.

The main frontend links here from its navbar via `VITE_FLIGHT_PLANNER_URL`
(default `/plan/`).

## How it relates to the rest of DroneTM

**The flightplan maths is not implemented here.** It comes from the QField
plugin's JS core in `src/qfield-plugin/{generate,output}/`, which is a port of
the Python `drone-flightplan` module. `plugins/vite-plugin-qmljs.ts` rewrites
those files from QML's JS-resource dialect (`.pragma library`, `.import`) into
ES modules at build time, so the plugin source keeps shipping to pilots
byte-identical and both clients run the same code.

`src/core/qfield.ts` is the only file that applies types to that core; the rest
of the app is fully type-checked TypeScript.

**The DEM path mirrors the backend.** `src/core/dem.ts` is a port of
`src/backend/app/dem/glo30.py`, down to the half-pixel grid origin, the
outward-only snapping and the 4096 px ceiling. That is deliberate: the browser
then samples the identical grid as the backend's per-project `dem.tif`, so the
two cannot disagree about the altitude of a waypoint.

## Tests worth knowing about

| Test                        | What it protects                                                                                                                                                                                                                                       |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `python-parity.test.ts`     | The important one. Runs the core over the committed AOIs and compares against fixtures generated by the **Python module itself** - count, flight time, battery warning, and every waypoint's coordinates, heading and photo flag. Python is canonical. |
| `dem-snap.test.ts`          | Mirrors `src/backend/tests/test_dem_glo30.py`, whose expected bounds were verified against direct GDAL reads of the source COGs. Proves the TS port is the same function as the Python one, including across a 1° tile seam.                           |
| `dem-sample.test.ts`        | Sampling against a real GLO-30 crop fixture: float32, no nodata tag.                                                                                                                                                                                   |
| `qmljs-transform.test.ts`   | Asserts the exported symbol set of every QField module, so a plugin edit that the transform cannot see fails here instead of at runtime in a field.                                                                                                    |
| `placemarks-parity.test.ts` | Pulls the pre-move implementations out of git and checks `generate/placemarks.js` still matches them exactly.                                                                                                                                          |
| `golden.test.ts`            | Locks six plan configurations, including ones with no Python fixture, so an unintended change shows up as a precise diff.                                                                                                                              |
| `dom-contract.test.ts`      | `main.ts` reaches into `index.html` by id with non-null assertions; this keeps both halves in step without a browser.                                                                                                                                  |

Regenerate the goldens deliberately, and check `python-parity.test.ts` still
passes afterwards - a golden update that silently breaks parity is the failure
mode this pair exists to prevent:

```bash
GOLDEN_UPDATE=1 pnpm test
```

Regenerate the Python reference fixtures only when `drone-flightplan` itself
changes:

```bash
cd ../backend
uv run --with pyproj --with shapely python \
  ../flight-planner/tests/fixtures/dump_python_waypoints.py \
  ../flight-planner/tests/fixtures/aoi-small.geojson \
  > ../flight-planner/tests/fixtures/python-aoi-small.json
```

## UI

`@hotosm/ui` 2.x, which wraps WebAwesome - `<wa-*>` components plus
`<hot-file-input-dropzone>`. No framework; a four-step wizard
does not need one. All colour, spacing and type comes from the `--wa-*` tokens
the HOT theme sets, so the app inherits branding and both colour schemes
without redefining any of it. Type is the platform sans stack, like every other
HOT tool - see [MADR 0014](https://docs.hotosm.org/decisions/0014-system-fonts).

The theme is switched on by the class list on `<html>`, guarded by
`dom-contract.test.ts`:

| Class                                  | Without it                                                       |
| -------------------------------------- | ---------------------------------------------------------------- |
| `wa-theme-default` `wa-palette-hotosm` | WebAwesome rules with real specificity outrank the HOT theme     |
| `wa-brand-red`                         | `variant="brand"` renders WebAwesome blue `#344f7b`, not HOT red |
| `wa-cloak`                             | Custom elements flash unstyled before they upgrade               |

`wa-brand-red` is the non-obvious one. `hot-wa.css` maps `--wa-color-brand-*`
in `@layer wa-color-palette`, but WebAwesome's own `:where(:root)` blue mapping
sits in the later `@layer wa-color-variant` - and a later layer beats any
specificity in an earlier one, so `wa-palette-hotosm` alone does not help.
`wa-brand-red` points brand at `--wa-color-red-*`, which the HOT palette owns.
The same trap applies to `--wa-color-success-*`, which is why "done" renders
WebAwesome green rather than HOT's teal.

Map colours come from the same place: `--dtm-map-*` in `app.css` derive from
`--wa-*`, the legend swatches use them, and `map/palette.ts` resolves them for
MapLibre's paint properties, which cannot take `var()`.

The tutorial is built into the wizard rather than bolted on: each step has a
coach card above its primary action and supporting detail below it, and every
input carries its own hint. Hints stay on with the tutorial off, because a unit
or a sensible range is not hand-holding. `?tutorial=0` or the header toggle
turns the coaching off; video guides are an optional link, never the primary
explanation.

## Layout

Mobile is the target - a pilot planning a flight is standing in a field with a
phone - but one DOM serves both shapes:

- **Phone.** The map fills the screen and the wizard is a bottom sheet over it,
  at one of three detents: `peek` (rail and Back/Next only), `half` (default)
  and `full`. Drag the grip, tap to cycle, or use the arrow keys. Steps that
  act on the map drop the sheet to `peek` and restore it once the map reports
  back.
- **Desktop.** Past 900px the sheet becomes the left sidebar, the grip is
  hidden, and `sheet.ts` no-ops.

The sheet covers the map rather than resizing it, so `fitBbox` pads for the
hidden part - after the height transition settles, or it pads for where the
sheet just was. `map/index.ts` keeps MapLibre's size in step with its container
for the same reason: the header grows after first paint, and a stale canvas
size skews every fit.

## Saved plans

Plans live in OPFS, one directory each, listed from `meta.json` alone. Three
things keep that list usable at twenty plans:

- `savePlan` writes nothing until there is an area, so an abandoned visit
  leaves no row. Handoffs are the exception - their fetched settings have to
  survive going offline.
- `planLabel` names an unnamed plan by date and area; the wizard never asks.
- Rows can be deleted, renamed, or have just their terrain freed - the DEM is
  nearly the whole footprint and is re-downloadable.

`pruneEmptyPlans` clears plans with no `aoi.geojson` after a week, the residue
of an earlier save path.
